# ТЗ: Система эволюции знания для кодинг-агента

**Кодовое название:** `evolve` (рабочее, заменить при желании)
**Версия документа:** 0.3 (черновик для обсуждения)
**Статус:** к согласованию

**История версий**
- 0.1 — первичная структура.
- 0.2 — дополнения по материалам [«Rethinking AI Agents: The Rise of Harness Engineering»](https://www.youtube.com/watch?v=Xxuxg8PcBvc): стоимость как first-class метрика (§10.3), верификатор как абляционный модуль (§11.4), ablation-инфраструктура (§12.4), harness-политика как версируемый NL-документ (§5.1), transfer-тест в canary (§9, §14.5), meta-оптимизация (§15, M6).
- 0.3 — по материалам [TencentDB Agent Memory](https://github.com/TencentCloud/TencentDB-Agent-Memory): white-box drill-down как требование к модели данных (§7.2), гибридный retrieval BM25+vector+RRF с budget-гвардами (§10.1), ссылка на источник (§20).

## 1. Назначение

Система накапливает, верифицирует и применяет знания (скиллы, хурики, уроки, факты, предложения тулов) из успешно выполненных задач и ревью работы агента. Знание применяется при будущих задачах, повышая success-rate и снижая повторение ошибок.

Ключевое свойство: **запись в базу — gated и частично автоматическая, применение — автоматическое, «эволюция» — метрик-драйвенная (telemetry), а не LLM-драйвенная**. Человек (один разработчик) выступает не ревьюером каждого кандидата, а еженедельным аудитором системы.

## 2. Цели

1. Накопление знаний из двух источников: завершённая задача (успех, подтверждённый верификатором) и структурированный фидбэк (человек или критик-агент).
2. Автоматическая эволюция (промоут/демоут/merge/депрешн) на низкорисковом подмножестве кандидатов без участия человека.
3. Еженедельный отчёт и очередь исключений, перерабатываемые за ≤ 20 минут.
4. Алерты на сигналы деградации (бюджет, противоречия, падение success-rate, чирн).
5. **Agent-agnostic ядро**: смена агента/модели не требует пересборки системы и не обнуляет базу знания.
6. Измеримое «умение»: тренды success-rate и повторения ошибок класса.
7. Стоимость (токены/compute на задачу) отслеживается наравне с качеством: улучшение качества при росте стоимости без учёта — регрессия.

## 3. Не цели (out of scope v1)

- Файн-тюнинг моделей.
- Мультипользовательность, SSO, публичный API, каталогизация.
- Автогенерация кода тулов (тул — это *предложение* в очереди, код пишет человек).
- Распределённая архитектура, HA.
- Ревью-интерфейс для команды (критик-агент — да, человек-коллег — нет).

## 4. Ограничения и предположения

| # | Предположение |
|---|---|
| A1 | Разработчик один; доступное время на систему — 15–20 мин/нед. + 1 ч/мес. |
| A2 | Один основной агент (DSH) на старте; мультиагентность — через адаптеры, не через ядро. |
| A3 | Верификация успеха задачи возможна автоматически для ≥ 50% типов задач (тесты, lint, smoke). Остальное — ручной флаг «подтверждаю успех». |
| A4 | Доступен LLM-API для экстрактора, детектора конфликтов и drift-проверки. |
| A5 | Объём базы ограничен: потолок ≤ 300 active-элементов. |
| A6 | Работа с кодовой базой — локально, git — источник истины для provenance. |

## 5. Стек (рабочее решение, меняется в фазе M0)

- **Ядро:** TypeScript, Node 20+ (единый бинарник: service + CLI).
- **Хранилище:** PostgreSQL 16 + `pgvector`. Векторная БД — только индекс; источник правды — SQL.
- **UI:** одна страница очереди + одна страница недельного отчёта (SSR, без фреймворков).
- **Конфиг:** один YAML-файл всех порогов/бюджетов (все гейты параметризованы).
- **Тесты:** детерминированная логика (стейт-машина, гейты, scoring) покрыта юнит-тестами; retrieval — golden-набор из 30–50 задач.

### 5.1 Harness как версируемый объект

«Harness» агента — вся оркестрация вокруг модели: harness-политика, retrieval-адаптер, формат и объём инъекции, гейты, бюджеты, canary-правила — фиксируется в **harness-документе** (естественный язык, git-версируемый, diff-абельный) и параметризуется конфигом порогов. Harness — first-class объект:

- каждая смена harness-политики — коммит с diff и ссылкой на данные (по мотиву [«Natural-Language Agent Harnesses»](https://arxiv.org/abs/2603.25723): перенос control-логики из кода в NL-представление сам по себе дал 30.4% → 47.2%);
- harness-документ обязателен для ablation (п. 12.4) и transfer-тестов (п. 14.5);
- meta-оптимизация (M6) работает именно с этим документом.

## 6. Глоссарий

- **Знание (item)** — версируемый элемент базы: skill / heuristic / negative / fact / tool-proposal.
- **Кандидат (candidate)** — черновик знания до прохождения гейтов.
- **Провенанс** — привязка к источнику: task_id, transcript_hash, commit, источник (success | review | critic).
- **Риск-тир** — low / high, определяет, требуется ли человек для промоута.
- **Canary** — тень: знание извлекается, но его метрики отдельно; промоут в active — по метрикам окна.
- **Score(item, agent)** — телеметрический рейтинг пары «знание × агент».
- **Чирн (churn)** — частота demotion за период; сигнал гнили.
- **Harness агента** — вся оркестрация вокруг модели: политика (документ, §5.1), retrieval, гейты, бюджеты, верификация. Отдельный от базы знания объект.

## 7. Модель данных

### 7.1 Таблицы (DDL-уровень)

```sql
items (
  id            uuid pk,
  type          text check (skill|heuristic|negative|fact|tool_proposal),
  title         text,
  scope         text,           -- модуль/glob/«all»; определяет широту
  tags          text[],
  applies_to    text,           -- 'all' | agent/model id
  status        text,           -- candidate|queued|canary|active|deprecated|archived
  risk_tier     text,           -- low|high (вычисляется гейтами)
  version       int,
  body          text,           -- тело текущей версии
  body_hash     text,
  embedding_id  text,           -- ссылка на индекс (pgvector)
  score_global  real,           -- агрегированный
  created_at, updated_at,
  archived_reason text
)

item_versions (id, item_id, version, body, body_hash, embedding_id,
               created_at, superseded_by)   -- иммутабельная история

provenance (id, item_id, version, source_type,  -- success|review|critic|human
            task_id, transcript_hash, commit, payload jsonb, created_at)

usage_log (id, item_id, version, agent_id, task_id,
           task_success bool null,      -- заполняется верификатором позже
           retrieved_at)

decisions (id, item_id, version, kind,  -- promote|reject|demote|merge|archive|approve_edit
           actor text,                   -- 'auto:<gate>' | 'human'
           reason text, evidence jsonb, created_at)

gate_results (id, candidate_id, gate,    -- dedup|conflict|scope|budget|evidence
              result, detail jsonb, created_at)

contradictions (id, item_a_id, item_b_id, severity, status,  -- open|resolved
                resolved_by, created_at)

agent_profiles (agent_id, context_budget, retrieval_top_k, format,
                created_at)
```

### 7.2 Требования к модели

1. Жёсткого DELETE нет: только `archived` + `archived_reason` (аудит).
2. Тело версии иммутабельно: любое изменение — новая версия + diff в `decisions`.
3. Каждое изменение статуса — запись в `decisions` (кто, почему, доказательство).
4. `score` не хранится как единственный источник правды: он всегда пересчитывается из `usage_log` (идемпотентный пересчёт по cron).
5. Embedding хранится на *версию*, не на item: старые версии остаются searchable для аудита.
6. **White-box и drill-down (hard requirement):** у каждого active item существует человекочитаемое артефактное представление — rendered body (Markdown) + сводка провенанса (задачи, коммиты, источник) — доступное без доступа к БД (CLI: `evolve item show <id>`). Диагностика неверного recall — *детерминированный drill-down* по цепочке: item → версия → provenance → исходная задача (транскрипт/коммит), а не «посмотрел косинусные скоры». Принцип: «нижние слои хранят доказательства, верхние — структуру» (паттерн [TencentDB Agent Memory](https://github.com/TencentCloud/TencentDB-Agent-Memory): Persona → Scenario → Atom → Conversation).
7. **Обратимость сжатия:** body (структура) отделён от сырых payload (доказательства); из любой версии любого item восстанавливаются исходная задача и первоисточник (transcript/commit по provenance). Необратимое суммарирование без сохранённого пути к источнику запрещено.

## 8. Типы знания и правила записи

| Тип | Пример | Типичный risk_tier | Источник |
|---|---|---|---|
| `fact` | «миграции БД лежат в `db/migrations`, формат foo» | low | success, review |
| `heuristic` | «при изменении схемы сначала прогоняй migration-тест» | low (узкий scope) / high (scope=all) | success, review |
| `negative` | «никогда не удаляй миграцию» | **high** | review, critic |
| `skill` | процедура: цель/шаги/ловушки/критерий готовности | low (узкий) / high (широкий) | success, review |
| `tool_proposal` | «нужен тул X» | **high** (всегда, это код) | любой |

Правило записи: **единственный путь создания item — кандидат + гейты**. Прямая запись в `active` запрещена на уровне API (даже вручную — через `decisions` с actor=human).

## 9. Конвейер

```
[триггер: success | review | critic]
        ↓
[Экстрактор LLM] → кандидат (структурированный, по схеме)
        ↓
[Гейты (синхронные, дешёвые, конфигурируемые)]
   G1 evidence   — есть task_id + верификация (не self-reported)
   G2 dedup      — cos_sim с base ≥ θ_dedup(0.85): не новый item, а merge-предложение
   G3 conflict   — LLM-детектор противоречий с active; найдено → contradictions.open
   G4 scope      — широта: scope='all' → high; привязка к файлам/модулю → low
   G5 budget     — лимиты: active ≤ 300; queue/нед ≤ 10; кандидатов/агент/день ≤ 5
        ↓
[решение по risk_tier]
   low  → [canary]
   high → [queue] (человек)
        ↓
[Canary] окно: 7 дней ИЛИ ≥ 3 retrievals (что наступит позже)
   pass:   retrievals ≥ 3 И success-rate(c) ≥ baseline − ε(5%)  → active (авто, decision=auto:canary)
   fail:   → candidate + flag; повтор — только новым кандидатом (решает человек в еженедельном окне)
        ↓
[Active] — в выдаче retrieval
        ↓
[Деградация] (cron, ежедневно)
   - score(item,agent) < θ_score(0.3) и used ≥ 5  → demote → deprecated (авто, логируется)
   - 21 день без usage                            → deprecated (авто)
   - drift (см. 9.2)                              → deprecated ИЛИ в queue (если scope широкий)
   - contradiction открыта > 7 дней              → оба в queue (человек)
        ↓
[Deprecated → Archived] через 30 дней, если score не восстановился
```

### 9.1 Стоимость в canary (cost-gate)

К canary-pass добавляется условие по стоимости: средние токены на задачу с применением элемента ≤ baseline × 1.2 (коэффициент в конфиге). Accuracy прошёл, cost не прошёл → элемент не в active, а в очередь с флагом `cost_only` (решение: оставить, править scope/объём body, отклонить). Основание: «тот же pass rate при 14× compute» — не эквивалентность, а регрессия (данные из видео/статей по harness engineering).

### 9.2 Drift-проверка (еженедельный cron)

Для item с `scope`, привязанным к файлам: LLM сверяет утверждения body с текущим состоянием файлов (diff по commit из provenance). Изменилось → кандидат на deprecate с diff в evidence. Это защита от «гноящейся» базы при эволюции кода.

## 10. Retrieval и применение

### 10.1 API

```
POST /retrieve
{ "query": str, "scope_hints": [..], "agent": str, "top_k": int }
→ [ { item_id, version, body, score, type, provenance_refs } ]
```

Retrieval — **гибридный**: BM25/FTS (Postgres full-text, tsvector) + vector (pgvector), фьюжн RRF, затем rerank:

```
candidates = RRF(bm25(query), vector_sim(query))   # оба канала на общих top-N
ranking    = rrf_rank · w1 + item_score(agent) · w2
           + scope_match · w3 − recency_decay · w4
(веса в конфиге; w2 — score именно для запросившего агента, fallback global)
```

Обоснование гибрида: знание о коде содержит идентификаторы, имена функций, пути к файлам — на них keyword-канал стабильно сильнее векторного; векторный канал ловит семантический парафраз. Дефолт — hybrid, `keyword`/`embedding` — переключатели в конфиге (паттерн [TencentDB Agent Memory](https://github.com/TencentCloud/TencentDB-Agent-Memory): BM25 + vector + RRF).

**Budget-гварды (обязательные, в конфиге):**
- `max_chars_per_item` — лимит символов на один инжект-элемент (default: включён; `0` = отключено — только как осознанный эксперимент);
- `max_total_recall_chars` — суммарный символьный бюджет авто-retrieval;
- timeout (default 5 c): по таймауту инъекция **пропускается, задача не блокируется**, инцидент логируется;
- overhead инъекции входит в метрику «токены/задачу» (§11.2, п. 7) и учитывается cost-gate (§9.1).

### 10.2 Адаптер агента

Из `agent_profiles`: формат контекст-блока (markdown / JSON / tool-call), бюджет токенов, top_k. Адаптер — тонкий слой на клиенте, ядро не знает о формате.

### 10.3 Правило применения

- Извлекаются только `active` (+ canary для метрик).
- Каждый факт использования → запись в `usage_log` **до** начала задачи (чтобы метрика была честной: «знание было доступно»).
- Negative-элементы извлекаются отдельно (блок «не делай») при совпадении scope.

## 11. Телеметрия и метрики

### 11.1 События

| Событие | Поля |
|---|---|
| `task_started` | task_id, agent_id, scope_hints |
| `knowledge_used` | task_id, item_id, version, agent_id |
| `task_verified` | task_id, success (bool), verifier (tests\|lint\|smoke\|human) |
| `review_recorded` | task_id, source (human\|critic), rating, issues[] |

### 11.2 Ключевые метрики (хранят тренды по неделям)

1. **Success-rate задач** (по верификаторам) — основной индикатор «умения».
2. **Ошибка-повтор**: частота попадания в уже известную *категорию* проблемы (из provenance). Цель: монотонное снижение.
3. **Покрытие**: доля задач, где retrieval вернул ≥ 1 элемента с score выше порога.
4. **Чирн**: demotion-ы/нед. Нормальный диапазон: 0–3.
5. **Здоровье базы**: доля active, не затронутых contradictions и drift-флагами.
6. **Точность гейтов** (косвенно, по audit-выборке): доля авто-решений, которые человек бы изменил.
7. **Стоимость** (first-class, наравне с качеством): токены/задачу (включая инъекцию, тул-вызовы, ретраи) и overhead контекста от базы. Стоимость не измеряется, если нет логирования token-использования на уровне задачи — это требование к M2.

### 11.3 Per-(item, agent) score

`score = 0.5·success_rate(used≥5) + 0.3·usage_norm + 0.2·recency`. Пересчёт idempotent, по cron ежедневно. Раздельный score на агента — обязателен (см. 14).

### 11.4 Верификатор как модуль, а не аксиома

Явный верификационный модуль не всегда полезен: в ablation-исследованиях harness'ов (цит. из [видео](https://www.youtube.com/watch?v=Xxuxg8PcBvc)) добавление Verifier *ухудшало* результаты на отдельных классах задач (−8.4 OSWorld). Поэтому:

- верификатор — абляционный модуль наравне с остальными (§12.4), а не безусловное благо;
- событие `task_verified` получает поля `verifier_id` и опциональный `human_override`;
- monthly audit (§12.3) включает таблицу: success по классам задач с верификатором / без (там, где класс позволяет обходиться без него);
- решение «выключить верификатор для класса X» — в harness-политику (§5.1), а не в код.

## 12. Интерфейс человека

### 12.1 Недельное окно (≤ 20 мин)

1. **Очередь** (страница): карточки high-risk кандидатов. Карточка = diff (новое vs существующее), провенанс (ссылки на задачи/фидбэк), «цена бездействия» (сколько раз встречалась проблема), противоречие (если есть). Кнопки: принять / принять с правкой / отклонить (причина обязательная — строится в `decisions`, экстрактор учитывает частые причины).
2. **Diff-лог недели**: авто-решения (promoуты, demotion, merges) списком с одним кликом «вернуть» (rollback = новая версия/статус, запись в `decisions`, actor=human).
3. **Топ-5 открытых противоречий** с рекомендацией системы.
4. Метрики недели (п. 11.2) — 4 числа и тренды + cost-блок: токены/задачу и overhead контекста от базы (п. 11.2, п. 7).

### 12.2 Алерты (push/CLI, только сигналы)

| Сигнал | Порог (конфиг) |
|---|---|
| Бюджет исчерпан | active > 90% cap |
| Противоречия копят | open contradictions > 5 |
| Success-rate падает | −5% за 2 недели при росте базы |
| Чирн высок | demotion-ы > 5/нед 2 недели подряд |
| Очередь гниёт | карточка в queue > 14 дней |
| Стоимость выросла | токены/задачу > baseline + 15% за 2 недели |

Всё остальное время система молчит.

### 12.3 Месячный аудит (1 ч)

CLI-отчёт `evolve audit --month`: кластеры противоречий, unused-хвост, score-распределение по типам, точность гейтов по выборке, дрейф scope, cost-профиль (п. 11.2, п. 7), результаты ablation за месяц (п. 12.4). На его основе — правки порогов/бюджетов в конфиге и правки harness-документа (п. 5.1).

### 12.4 Ablation-инфраструктура («когда убрать структуру»)

Принцип из материалов по harness engineering: добавлять структуру — легко, а эффект добавления неочевиден (иногда отрицателен). Поэтому каждый активный модуль системы (dedup, conflict-детектор, negative-элементы в выдаче, canary, верификатор, критик) поддерживает режим off на неделю (флаг в harness-документе/конфиге). Ablation-отчёт: изменение success-rate и стоимости/задачу при отключённом модуле.

- модуль без положительного эффекта на качество, но с измеримой стоимостью → в месячный аудит как кандидат на отключение;
- решение об отключении принимает человек (еженедельное/месячное окно); отключение фиксируется в harness-документе — это и есть управляющий механизм;
- цель: система знает не только «что добавить», но и «что убрать».

## 13. Критик-агент (фаза M4)

- Отдельный промпт/модель, другой угол: «найди, где это сломается» (не «прочитай себя»).
- Вход: завершённая задача + её верификация. Выход — **структурированный** фидбэк:

```json
{ "rating": 1..5, "issues": [ { "type": "bug|design|missing|style|other",
   "severity": "low|med|high", "evidence": "file:line / тест / цитата",
   "lesson_candidate": "строка-урок" } ] }
```

- Фидбэк проходит конвейер как обычный триггер (critic — ещё один источник, не привилегированный).
- **Качество критика измеряется**: по телеметрии — на задачах с учётом его lesson-кандидатов success выше/ниже. Lожные issues (проверены и не подтверждены) снижают вес критика механически (`critic_weight` в конфиге, авто-пересчёт еженедельно).

## 14. Agent-agnostic требования (hard requirements)

1. Схемы данных, конвейер, метрики не содержат ссылок на конкретного агента. Агент — `agent_id` + профиль.
2. Каждый item может иметь `applies_to` (`all` | конкретный агент). Default: `all`.
3. Поведенческие уроки (про специфику модели) — только с `applies_to=<agent>`; retrieval фильтрует по профилю.
4. Score ведётся на паре (item, agent); global — агрегат.
5. Смена агента = новый `agent_profile` + canary-репрогон top-50 active-элементов на нём (не полная перепроверка базы).

### 14.5 Transfer-тест в canary

Motivation: [Meta-Harness](https://arxiv.org/abs/2603.28052v1) показал, что harness (и найденные в нём паттерны), оптимизированные на одной модели, переносятся на другие — переиспользуемый актив здесь *структура/политика*, а не модель. Поэтому:

- в canary-окне репрезентативная подвыборка (top-20 по importance) прогоняется как минимум на **альтернативном** `agent_profile` (другая модель/профиль);
- элементы, стабильно работающие только на одном профиле → тег `transfer:weak` (не блокирует active, но попадает в месячный аудит);
- harness-политика (§5.1) обязана быть исполнимой в профилях ≥ 2 моделей — hard requirement, проверяется на M5.

## 15. Этапы (milestones)

### M0 — каркас (неделя 1)
Схема БД, стейт-машина, CLI (`evolve item add/list/transition`), конфиг порогов, юнит-тесты стейт-машины и гейтов (на мок-LLM).
**Критерий:** можно вручную прогнать кандидата через все гейты и статусы; каждый переход оставляет `decisions`.

### M1 — экстрактор + гейты (недели 2–3)
Триггер «успех задачи» (интеграция с верификаторами DSH/тестов), LLM-экстрактор по схеме, гейты G1–G5, CLI-очередь (карточки в терминале, причины отклонения).
**Критерий:** на 20 реальных завершённых задачах: ≥ 70% кандидатов проходят G1–G5 без участия человека; ложных кандидатов (которые человек бы отклонил) в выборке ≤ 3.

### M2 — retrieval + телеметрия + canary (недели 4–5)
pgvector-индекс, `/retrieve`, адаптер DSH (контекст-блок), запись `usage_log`, canary-окно, auto-promote, per-(item,agent) score.
**Критерий:** на golden-наборе 30 задач retrieval-качество (recall@5) ≥ 0.7; canary-цикл прогнан end-to-end без ручного вмешательства.

### M3 — отчётность, decay, drift (неделя 6)
Недельная страница (очередь + diff-лог + метрики), алерты, ежедневный cron degrading, weekly drift-проверка, monthly audit CLI.
**Критерий:** недельное окно укладывается в 20 мин на базе отчёта; rollback любого авто-решения — в 1 клик.

### M4 — критик и review-триггер (неделя 7+)
Критик-агент, review-триггер (включая ручной фидбэк человека — форма: оценка + issues), авто-вес критика, `tool_proposal`-поток.
**Критерий:** 2 недели работы: ≥ 50% lesson-кандидатов критика проходят гейты; вес-механика видна в отчёте.

### M5 — стабилизация (после месяца эксплуатации)
Первые данные: точность гейтов, пороги по факту, бюджет по факту. Тонкая настройка конфига. Проверка agent-agnostic (п. 14) + transfer-тест (п. 14.5) на втором профиле.

### M6 — meta-оптимизация harness-политики (исследование, после M5)
Outer-loop по мотивам [Meta-Harness (Stanford)](https://arxiv.org/abs/2603.28052v1): agentic proposer получает доступ к `decisions`, `usage_log`, результатам гейтов и скорам (через файловую систему, как в статье — «богаче доступ к прошлому опыту» и есть источник эффекта) и предлагает **кандидатные правки harness-документа** (§5.1): пороги, бюджеты, формат инъекции, ablation-флаги.

- каждый кандидат — новая версия документа в git + diff в обычную очередь (человек);
- промоут кандидата только если: success-rate на golden-наборе ≥ baseline + 5 п.п. И стоимость токенов/задачу ≤ baseline (cost-gate, п. 9.1);
- proposer не меняет harness напрямую — только предложения; решения принимают человек + метрики.

## 16. Риски и митигации

| Риск | Митигация |
|---|---|
| Качество LLM-экстрактора низкое | Метрика «ложных кандидатов» (M1-критерий); схемы+few-shot в промпте; причины отклонений → итеративная доработка экстрактора |
| Галлюцинированные «уроки» попадают в базу | G1 (обязательный верифицированный provenance) + canary + demotion по score |
| Конфликт-детектор пропускает противоречие | Еженедельный аудит + метрика «здоровье базы» + ручной флаг на item |
| База сжимается в пустоту (over-pruning) | Порог demotion только при used≥5; monthly audit смотрит на unused-хвост и score-распределение; cap на долю deprecated за месяц (20%) |
| Очередь не читается (рот) | Алерт «карточка > 14 дней»; лимит queue/нед; ранжирование по цене бездействия |
| Метрика success-rate искажена (верификатор слабый) | Инвестиция в верификаторы как отдельный трек (п. 17); пометка `verifier=human` отдельно в статистике |
| Один разработчик = SPOF | Всё состояние в SQL + git (конфиг, конфиг-изменения коммитятся); восстановление = restore БД + конфиг; документированный runbook |
| Качество растёт, но «дорого» (токены/compute) | cost-gate в canary (п. 9.1), алерт по стоимости, cost-профиль в exit-criteria |
| Модуль «вредит», но не замечено | ablation-инфраструктура (п. 12.4): режим off на неделю у каждого модуля |
| Harness — непроверяемый «чёрный ящик» | harness-документ: версируемый, diff-абельный, NL (п. 5.1) |

## 17. Отдельный трек (параллельный, критичный)

**Укрепление верификаторов.** Качество всей автономии ограничено качеством ответа на «задача выполнена хорошо?». Список: тесты под ключевые типы задач, lint/typecheck в пайплайне, smoke-сценарии, формализованный ручной флаг успеха для неверифицируемого. Целевое покрытие: ≥ 80% типов задач к M3.

## 18. Определение «умнее» (exit-criteria проекта, 3 месяца)

1. Success-rate (по верификаторам) выше baseline на ≥ 10 п.п. на сопоставимых задачах. Улучшение качества без cost-профиля (п. 11.2, п. 7) не засчитывается: токены/задачу — не выше baseline до M2 либо обоснованы в harness-документе.
2. Ошибка-повтор (категории, о которых база знает) сократилась ≥ 2×.
3. Еженедельное окно стабильно ≤ 20 мин в течение 4 недель.
4. База в пределах cap (≤ 300 active) и ≥ 60% active имеют used ≥ 3 за 30 дней.

## 19. Открытые вопросы

1. Формат контекст-инъекции в DSH: системный блок или отдельный тул `context_lookup`? (Влияет на M2; оба варианта поддерживаются адаптером.)
2. Граница «успеха» для неверифицируемых задач: только ручной флаг или допустимо «завершение + критик ≥ 4/5» (после M4)?
3. Хранить ли полные транскрипты задач (для аудита/перевыбора) или только хеши + выжимки? (Объём vs глубина аудита.)
4. Пороги: θ_dedup=0.85, ε=5%, θ_score=0.3, decay=21 день, cost-gate ×1.2 — стартовые значения, пересматриваются на M5 по фактическим данным.
